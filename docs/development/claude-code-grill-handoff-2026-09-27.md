## 8. grillの進め方

1. まず自分でコード/正本/票を調べる。調べれば分かる事実を利用者への質問にしない。連携が無ければ読めない範囲を明記し、承認を捏造しない。
2. 状態を「決定済み / 未決 / 実装済み / 実接続未完了 / 監修待ち」で整理。一律「未対応」に戻さない。
3. 1回の返答で意思決定の質問は1つ。推薦回答・理由・代替案との不利益・影響票を短く添えて回答を待つ。以前長すぎたため、既決の同義質問や微小な通常実装判断を増やさない。
4. 高リスク判断を一括の「はい」に混ぜない。必要な枝だけ深掘りし、本人の回答文・対象問・採否・残条件を対応させる。
5. 回答後は当該小票と対象SSOT→ADR→別repoの読者仕様/設計へ反映する。新判断なしなら無意味なADRを増やさない。決定責任者は會田、未回答推薦を「會田承認」と記さない。
6. 節目で共有理解を確認してから、明示された実装範囲を小契約にする。grill引継ぎだけで新しい実装を開始しない。アプリコード・秘密設定・インフラを勝手に変更しない。
7. 実装を別途依頼されたら既存開発スキルの否定試験・変更契約・検証を実施。未接続票/Gは残し、当該受入を満たした範囲だけ完了とする。

## 9. 引継ぎ先への最初の出力
