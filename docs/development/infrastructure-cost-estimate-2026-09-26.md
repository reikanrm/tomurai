## 6. 復旧と予算承認の境界

大阪の日次backupと東京のPITRだけでは、東京リージョン障害時のRPO1時間を満たす根拠にならない。PITRのログはprimary側リージョンにあり、replicaは非同期である。本案の稼働中replicaも**RPO≦1時間/RTO≦4時間を保証しない**。[Backupの比較](https://docs.cloud.google.com/sql/docs/postgres/backup-recovery/backup-options)、[クロスリージョン復旧](https://docs.cloud.google.com/sql/docs/postgres/replication/cross-region-replicas)

Standard backupの保存先を大阪へ明示する候補とする。デフォルトのasia multi-regionを国内限定と解釈しない。Enhanced backupのcross-region制約を確認せず置き換えない。replicaには誤削除も伝わり、standard backupだけでproject削除耐性があるとも扱わない。独立復旧コピー・削除台帳の保護方針は別判断を要する。

Enterpriseでの大阪昇格は手動DR。復旧時には大阪のHA化/追加費用も検討する。DB昇格に加え、障害検知、旧系の書込み停止、API・認証・secret・接続切替、削除/同意撤回/最新権限の再適用、送信workerの単一稼働と二重送信防止を含む全体時間を測る。Cloud Runを二地域に置くだけでは自動failoverは成立しない。[Cloud Run multi-region](https://docs.cloud.google.com/run/docs/multiple-regions)

G01の予算アラートは強制支出上限ではない。通知が遅れる可能性やバックアップ/DBの固定費を考慮し、危険な自動DB停止をしない。予算閾値・通知先・AI/LINE上限・運営承認・緊急時の停止範囲は後続grillで決める。

今回の承認は「この3段階を見積ってから予算を判断する」ことだけ。公式料金の読み取りと文書/Linear更新を行い、クラウド作成、設定変更、送信、課金、デプロイは行っていない。G01/G02/G05をDoneにしない。
